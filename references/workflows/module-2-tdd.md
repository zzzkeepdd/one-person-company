# TDD 开发流程

## 前置

用户已确认《需求规格说明书》。节点门2 已通过。

## 流程

### 步骤 0: 管道判定

确认风险级别（L1/L2/L3），按管道分发：

| 管道 | 开发主体 | 验收链 |
|------|----------|--------|
| L1 | Hermes 直接写代码 | code-qa + func-qa 强制独立，不可跳过 |
| L2 | Codex TDD | code-qa + func-qa 独立（缩减版：缺陷清单，不写完整分析） |
| L3 | Codex TDD | code-qa + func-qa 独立（完整版） |

### 步骤 0.5: 信息瓶颈 + 节点门3

模块二启动时只注入执行清单 JSON（~200 token），不注入原始需求描述和辩论历史。

运行 `python scripts/validate_execution_manifest.py <执行清单JSON路径>`：
- tasks 非空 ✓ → 继续
- spec_checksum 匹配 ✓ → 继续
- 不通过 → 拒绝执行，回模块一修复

需要细节时通过 full_spec_path 按需回查规范文件。

### 步骤 1: 健康检查（L2/L3）

`codex --version` → 不可用立即止损，通知用户。

### 步骤 2: 准备 Codex（L2/L3）

确认 MCP 已挂载。按 prerequisite.md 初始化。

### 步骤 3: 任务分级

对照执行清单 JSON 分级：
- UI纯视觉 → 代码技术验收（跳过集成测试和e2e）
- 逻辑改动 → 完整TDD链
- 配置/文档 → 跳过测试

### 步骤 4: 派发开发

**L1**: Hermes 直接按 tasks[] 逐个写文件，每完成一批用 read_file 验证头尾。
**L2/L3**: 开发统筹将任务分发至 AI程序员/前端开发/开发执行 → Codex 产出代码 + 测试。

### 步骤 5: 文件落盘验证

每批产出后 read_file 头 3 行 + 尾 3 行确认文件存在且完整。

---

### 【硬闸门】步骤 6: 强制验收链

开发统筹在收到开发者交付的代码后，必须严格执行以下闸门规则。此闸门不可跳过、不可替代、不可自行判断。

**闸门规则：**

1. **强制创建验收Agent。** 开发统筹必须委托 code-qa Agent 和 func-qa Agent。不允许用任何理由跳过（包括但不限于：pytest全绿、代码简单、时间紧迫、自己看过了）。

2. **强制产出报告。** code-qa 产出《代码技术验收报告》。func-qa 产出《功能业务验收报告》（含浏览器实操）。两份报告必须独立存在，不可合并为单文件。

3. **缺报告 = 驳回。** 任一份报告不存在 → 当前版本直接驳回，不准进入下一阶段。整改后重新走完整验收链。

4. **L1 降级规则。** L1 管道 QA 失败 ≥2 次 → 自动降级 L2，走 Codex TDD。

5. **开发统筹降格为调度员。** 开发统筹不准自行判断代码是否通过。收集完两份报告后 → 向赫尔墨斯统筹发送"项目交付请求"，附带：两份报告路径、复杂度分级文件路径、项目根目录路径、管道级别。赫尔墨斯统筹收到请求后，必须运行 `python scripts/harness_auditor.py --pipeline <l1|l2|l3> <项目目录> <harness根目录>`。审计通过 → 通知用户项目完成。审计不通过 → 打回，项目状态改回"开发中"，附审计失败原因。

**验收链执行顺序：**
- 代码技术验收(code-qa)：集成测试 → 静态检查 → 安全扫描 → 产出报告
- 功能业务验收(func-qa)：e2e测试 → 覆盖率检查 → 功能比对 → 浏览器实操 → 产出报告
- 任一步失败 → 整改协调Agent分析根因 → 重新派发 → 重新走完整验收链

---

**步骤 7: 交付。** 两份验收报告均通过 → 审计闸门通过 → Hermes 呈用户验收（附两份报告）。
