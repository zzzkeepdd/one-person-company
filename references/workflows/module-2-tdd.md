# TDD 开发流程

## 前置
用户已确认《需求规格说明书》。

## 流程

**步骤 1: 健康检查。** `codex --version` → 不可用立即止损，通知用户。

**步骤 2: 准备 Codex。** 确认 MCP 已挂载。按 prerequisite.md 初始化。

**步骤 3: 任务分级。** 对照需求分级：
- UI纯视觉 → 代码技术验收（跳过集成测试和e2e）
- 逻辑改动 → 完整TDD链
- 配置/文档 → 跳过测试

**步骤 4: 派发开发。** 开发统筹将任务分发至 AI程序员/前端开发/开发执行 → Codex 产出代码 + 测试。

**步骤 5: 文件落盘验证。** 每批 Codex 产出后 read_file 头 3 行 + 尾 3 行确认文件存在且完整。

---

### 【硬闸门】步骤 6: 强制验收链

开发统筹在收到开发者交付的代码后，必须严格执行以下闸门规则。此闸门不可跳过、不可替代、不可自行判断。

**闸门规则：**

1. **强制创建验收Agent。** 开发统筹必须委托 code-qa Agent 和 func-qa Agent。不允许用任何理由跳过（包括但不限于：pytest全绿、代码简单、时间紧迫、自己看过了）。

2. **强制产出报告。** code-qa 必须产出《代码技术验收报告》。func-qa 必须产出《功能业务验收报告》（包含浏览器实操报告）。两份报告缺一不可。

3. **缺报告 = 驳回。** 任一份报告不存在 → 当前版本直接驳回，不准进入下一阶段，不准通知用户"已完成"。整改后重新走完整验收链。

4. **开发统筹降格为调度员。** 开发统筹不准自行判断代码是否通过。收集完两份报告后 → 向赫尔墨斯统筹发送"项目交付请求"，附带：两份报告路径、复杂度分级文件路径、项目根目录路径。赫尔墨斯统筹收到请求后，必须运行 `python scripts/harness_auditor.py <项目目录> <harness根目录>`。审计通过 → 通知用户项目完成。审计不通过 → 打回，项目状态改回"开发中"，附审计失败原因。

**验收链执行顺序：**
- 代码技术验收(code-qa)：集成测试 → 静态检查 → 安全扫描 → 产出报告
- 功能业务验收(func-qa)：e2e测试 → 覆盖率检查 → 功能比对 → 浏览器实操 → 产出报告
- 任一步失败 → 整改协调Agent分析根因 → 重新派发 → 重新走完整验收链

---

**步骤 7: 交付。** 两份验收报告均通过 → 开发统筹上报 Hermes → Hermes 呈用户验收（附两份报告）。
