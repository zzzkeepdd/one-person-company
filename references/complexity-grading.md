# 复杂度分级

## 判定标准

| 维度 | 简单(L1) | 中等(L2) | 复杂(L3) |
|------|----------|----------|----------|
| 用户可见产品 | 否（API/库/CLI无UI） | 是（网页/App界面/GUI） | 是+品牌/设计要求 |
| 新文件数 | ≤ 3 | 4-15 | > 15 |
| 外部API | 无 | 1-2个 | 3+ |
| 并发/安全 | 无需考虑 | 基础安全 | 复杂并发/多角色权限 |
| 数据模型 | 无/单表 | 2-3表关联 | 复杂模型/迁移 |
| 技术栈 | 单一 | 2种 | 3种+ |
| 外部依赖 | 无（或仅stdlib） | 普通依赖 | 需要新系统级依赖 |

## 笼统需求处理

用户只说一句话（如"帮我开发一个量化平台"）→ 需求过于笼统：
1. 仍然走预澄清，但优先匹配领域模板（references/domain-templates.md）
2. 匹配到模板：注入默认值，用户只需改不吻合部分（改错比填空快）
3. 未匹配到模板：现场定义 3-7 个维度，每个维度带默认值
4. 笼统需求在预澄清阶段不得少于 2 轮 QA

## 阈值

- **L1（简单）**: 全部维度在"简单"列。触发附加判据：≤3文件改动 + 单一技术栈 + 无用户可见产品 + 无外部依赖声明
- **L3（复杂）**: 任意维度在"复杂"列
- **L2（中等）**: 其他所有情况

## 安全网

- 用户可见产品=是 → 至少 L2，不可走 L1
- L1 运行时：每 100 行自检，超阈值自动升级 L2
- L1 QA 失败 ≥2 次 → 自动降级 L2（Codex TDD）

## 分流

| 管道 | 流程 | 开发主体 |
|------|------|----------|
| L1 | 预澄清1轮 → Hermes直接写 → QA → 审计 → 交付 | Hermes |
| L2 | 预澄清 → 维度拆分 → 并行辩论1轮/维度 → 规范 → Codex TDD → QA → 审计 → 交付 | Codex |
| L3 | 预澄清 → 维度拆分 → 并行辩论1-2轮/维度+裁决 → 规范 → Codex TDD → QA(完整) → 审计 → 复盘提醒 → 交付 | Codex |
